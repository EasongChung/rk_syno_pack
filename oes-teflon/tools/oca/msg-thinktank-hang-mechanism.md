## 0. 背景（必读，30 秒版）

- 目标：让 Synology Photos 的照片主题识别走 A311D NPU。方案 = Mesa Teflon 用户态栈 + TFLite external delegate `libteflon.so`。
- 判定用四级判据：① 编译/分区不崩 ② 接管算子数 ③ 推理能执行完 ④ 输出与 CPU 基准逐字节一致。
- 当前状态：

| 路线 | ① | ② | ③ | ④ |
|---|---|---|---|---|
| CPU / float16 | ✅ | n/a | ✅ | ✅（该路线即基准，**唯一可交付**） |
| NPU per-tensor | ✅ | ✅ 153 | **❌ 作业挂死** | ❌ |
| NPU per-channel | ❌ SIGSEGV | ✅ 99→153 | ❌ | ❌ |

- **主线卡在 ③**：不是精度问题，是 NPU 作业挂死。已定位到最小挂死单元 = **单个 1×1 CONV（244 通道）**
  （报告 28，隔离/二分实验，4 轮一致）。内核表现为 `etnaviv_sched_timedout_job` → `recover hung GPU!` + core_dump + resubmit。

## 1. 源码机制候选（我方目前的主假设）

源码：`/root/clawtemp/mesa_src/etnaviv_ml_nn_v7.c`（Etna NNN v7 通路）

`calc_superblocks`（该文件 :20-40）在 `weight_width==1`、`nn_core_count=8`、`nn_accum_buffer_depth=64`、tile_y 使 `foo=5` 时导出：

```
kpc = ceil(C / 8)                      # kernels_per_core
sb  = ceil(kpc / 5)                    # superblocks
d   = ceil(kpc / sb)                   # DIV_ROUND_UP(kernels_per_core, superblocks)
rem = kpc - (sb - 1) * d               # 末批实际核数
```

`write_core_6`（该文件 :217-232）：

```c
for (unsigned superblock = 0; superblock < superblocks; superblock++) {
   unsigned kernels_in_superblock = DIV_ROUND_UP(kernels_per_core, superblocks);   // :219  == d
   if (superblock == superblocks - 1)
      kernels_in_superblock = kernels_per_core - kernels_in_superblock * (superblocks - 1);  // :220-221 == rem
   for (unsigned kernel = 0; kernel < kernels_in_superblock; kernel++) {
      unsigned out_channel = core * kernels_in_superblock + kernel
                           + superblock * DIV_ROUND_UP(kernels_per_core, superblocks) * cores_used;  // :224 / :231
      ...
```

⇒ 末批的每核基址用了 `core * rem`，但 `superblock * DIV_ROUND_UP(kpc, sb)` 仍是按 `d` 算的。
⇒ 末批每核基址比正确值少 `core * (d - rem)` 个 kernel，每 kernel 8 通道 ⇒ **错位量 = 8·(d − rem)**。
⇒ 越界通道数 = `8·kpc − C`（补齐到 8 的倍数后多出来的通道）。

**唯一存活的经验律（10/10 命中）**：

> **挂死 ⟺ `rem == 1` 且 `C` 不是 8 的倍数（等价于 `8·kpc > C`）。**

248 是关键对照：它与 244 的 `(kpc,sb,d,rem)` **完全相同**（31/7/5/1），仅越界为 0 ⇒ 不挂。

## 4. 我方自己承认的缺口（这是最需要智囊团帮忙的地方）

1. **经验律没有机制**。`rem==1` 与 `rem==2` 的差别，按 §1 的推导只是「基址少乘了几倍 core」，
   为什么一个越界读会挂、另一个同样越界却不挂，目前**解释不了**。越界通道数两者都是 4（244/284 vs 252）。
   可能的方向：越界读是否越过了**系数流末尾** / **img_cache 末尾** / 触发了非对齐地址 / 读到了 DMA 边界外；
   也可能根本不是越界，而是 `rem==1` 时 `kernels_in_superblock=1` 使 `weights_maps[]`/循环步进方式发生别的退化。
2. **数据量小**：只有一个正例族（244）与另一个正例（284），8 个负例。
3. **模型是合成件**，与真实模型（Synology Photos int8 主题识别模型）是否同通路，尚未逐项对齐。

## 5. 我方的方法学事故（供智囊团评估我的结论可信度）

- 第一轮细扫 8 点**全部假失败**：脚本拼模型名漏了 4 位补零 ⇒ `Could not open`。⇒ 任何"未跑起"必须与"不挂"区分。
- 第二轮 8 点**路径拼接重复**（传绝对路径又补前缀）⇒ 又一次全点假失败。
- `kern.log` 在 284 那次被轮转 ⇒ 计数法出现 `-112`，挂死判据退化为行为证据。
- **批量 + 无人值守**把 284 跑挂并导致整机失联，损失一次物理断电。⇒ 已冻结一切批量上机。
